# Working on Native Console

## Project and documentation map

Native Console turns console ROMs (Game Boy, Game Boy Color, Game Boy Advance, Super Nintendo, NES, Nintendo DS, Nintendo 64) into generated C and links that code with a per-console runtime.

The main areas are:

- `recompiler/`: Game Boy ROM loading, decoding, analysis, IR, code generation, and the `gbrecomp` CLI
- `runtime/`: Game Boy CPU fallback, mappers, PPU, DMA, timers, audio, persistence, SDL, and ImGui
- `recompiler-gba/`, `runtime-gba/`: the Game Boy Advance recompiler (`gbarecomp`) and runtime; see `GBA.md`
- `recompiler-snes/`, `runtime-snes/`: the Super Nintendo recompiler (`snesrecomp`) and runtime, SA-1 included; see `SNES.md`
- `recompiler-nes/`, `runtime-nes/`: the NES recompiler (`nesrecomp`) and runtime, with its cartridge boards; see `NES.md`
- `recompiler-nds/`, `runtime-nds/`: the Nintendo DS recompiler (`ndsrecomp`) and runtime, both processors; see `NDS.md`
- `recompiler-n64/`, `runtime-n64/`: the Nintendo 64 recompiler (`n64recomp`) and runtime, with the RSP and the RDP; see `N64.md`
- `lift/`: the checker that runs lifted Game Boy source against the original ROM code (`lift/checker/`); the interface that source is written against is `runtime/include/gblift.h`, and `runtime/src/gbrt_lift.c` is its implementation inside a generated game; driven by `tools/gb_lift.py`, see `LIFTING.md`
- `hub/`: the desktop hub (SDL2 + ImGui) that catalogues ROMs, runs the recompile/build pipeline per game, exports builds for other platforms, and launches executables; console backends live in `hub/src/console_*.cpp`
- `tests/`: repository-owned synthetic and unit regression tests; `tests/gba/`, `tests/snes/`, `tests/nes/`, `tests/nds/` and `tests/n64/` for GBA, SNES, NES, Nintendo DS and Nintendo 64
- `tools/`: accuracy, trace, differential-log, frame, audio, and benchmark helpers; `tools/gba/`, `tools/snes/`, `tools/nes/`, `tools/nds/`, `tools/n64/`, `tools/steamos/`, `tools/macos/` for GBA, SNES, NES, Nintendo DS, Nintendo 64 and platform builds; `tools/consoles.sh` is the console table the platform scripts share
- `roms/`: local test ROMs and fetched test suites (`roms/gba/`, `roms/snes/`, `roms/nes/`, `roms/nds/`); do not commit copyrighted commercial ROMs
- `output/`: ad hoc generated projects and launcher builds
- `logs/`: durable repro captures, state dumps, frame captures, and benchmark results

## Adding a console

Follow `docs/ADDING-A-CONSOLE.md`. Keep the generated-project contract it describes, so that hub builds, exports, and the Linux and macOS paths need no per-console code. Every console's runtime has an in-game overlay menu that meets the playbook's overlay requirements; the Game Boy settings menu is the reference. Record every phase gate in the console's `docs/<F>-PLAN.md`. Keep the backend behind `supported() == false` until the gates up to P6 pass. Copy code only from sources whose licenses the playbook allows, and record each port in `THIRD_PARTY.md`.

## Hardware references

For Game Boy hardware behavior, consult `tech_docs/pan_docs.md` first. Other consoles name their references in their plan (GBATEK for GBA; fullsnes and ares for SNES; the nesdev wiki and ares for NES; GBATEK and the BlocksDS hardware tests for Nintendo DS; ares, n64brew and krom's tests for Nintendo 64). Use the local `SameBoy/` source as the second reference when Pan Docs is ambiguous or a proven implementation is needed.

This is mandatory for timing-sensitive work, especially:

- CGB registers and DMG-on-CGB behavior
- mapper address resolution
- PPU modes, STAT, palettes, and bus visibility
- OAM DMA and HDMA
- timers, interrupts, HALT/STOP, and speed switching

## Build and test standards

Always use CMake with Ninja. The root project requires CMake 3.20 or newer.

```bash
cmake -G Ninja -B build . -DBUILD_TESTS=ON
ninja -C build
ctest --test-dir build --output-on-failure
```

Do not trust a relocated CMake cache. If a build directory points to a different checkout, configure a fresh build directory instead of treating its failure as a source regression.

The repository-owned CTest suite is the default fast gate. It covers analyzer state, mapper resolution, 9-bit MBC5 banks, bus phases, HALT/OAM-bug CPU transitions, PPU/DMA timing primitives, state/test-runner protocols, multi-ROM isolation, and release relocation.

The game and the export are made by one list of options (`analysis`), so that the tree's data is data to the game it stands beside: an option must never reach one and not the other. A step is done again only when what it was made from has changed (`step`, and the dictionaries of hashes in `workspace.json`), and the data tree is never among those things, since it is where the modder works: a new step has to say everything it reads and nothing of the tree's files. And no step may write over an edit: a tree is split again only with `--keep` into a folder beside it, with the old tree moved to `old/` and never deleted, `text` is run with `--keep-edited`, and nothing is run with `--force`. A command added to the tool has to behave so when it is run a second time on a tree somebody has worked in, or get an option that makes it. `uses` and `annotations` are given the folder of records and `unpacked` the folders of harvests, since a command line does not hold hundreds of file names; records and harvests only ever add up there. A save state made by a game run with `--no-audio` loads only in a game run that way (the size of the sound hardware's part in its header is nought): `made_with_sound` in `tools/gb_data_unpack.py` reads that, for `unpack --state` and for the tool's runs from save states.

Changes to `tools/gb_data_streams.py`, to `command_streams`, `with_stream` or `check_stream_view` in `tools/gb_data.py`, or to how that file reads any view back (`spans`, `check_views`, `with_views`), must run `data_streams_as_text`, and `data_keep_split_again` and `data_names_end_to_end` with it. `gb_data.py streams` writes a game's music and sound as the commands of its sound engine, from a declaration somebody writes (`streams.json`; `DATA_FILES.md`, *Music and sound as commands*), and knows no game's engine: nothing of one game's commands goes into the tool. Keep these true. Text written from bytes goes back into exactly those bytes, and that is settled when the declaration is read, not when a file is: every bit of a command is said by an operand or is the same for all the first bytes the command has in its grammar, and a line whose first byte would be another command's is refused. A new way to say or to write an operand has to keep both, or be refused in `load_declaration`. Nothing is guessed: a stream stops at the first thing it cannot read, with the address, and what was read before stays. Decoding reads through files of code and the header and writes no view of them, since a view is of whole commands in one data file. A passage keeps its place: it is cut wherever a start or a target points, so that nothing known points into the middle of one; more bytes are refused, and fewer are taken only where the passage's last command ends the stream, with what was after them left as it was. Whoever builds moving has to turn the table's entry and every target that leads to the passage, and cannot know the places a game's code points a channel at. The lines that passages start with are not edited: `said` holds a file to the passages its view records. And the check against the game played counts by the instruction `uses` wrote as the first to read a byte (`seen`), so a change to what `seen` says of a reader has to be looked at from `check` and `readers_found` too.

Native replacement changes must additionally run `native_patch_sdk_end_to_end`.
Keep `gb_native_call_original()` as a scheduling disposition: generated bodies
can return at safepoints before the guest function returns, so post hooks must
remain tied to the captured guest call frame rather than the native C stack.

## Required validation for generated behavior

Changes to analyzer logic, code generation, generated CMake, runtime behavior, or runtime headers must validate both the root build and a freshly generated project.

```bash
ninja -C build

./build/bin/gbrecomp <test-rom> -o output/<test-project>
cmake -G Ninja -S output/<test-project> -B output/<test-project>/build
ninja -C output/<test-project>/build
./output/<test-project>/build/<test-project> --headless --limit-frames 120
```

Use a legal local ROM for the smoke run. The synthetic CTest fixtures remain the portable CI gate. When a generated build appears to ignore a runtime change, regenerate and explicitly rebuild it; stale generated trees are a recurring source of false conclusions.

Apply focused external tests according to the subsystem:

```bash
python3 tools/run_tests.py --filter ppu
python3 tools/run_tests.py --filter oam_dma
python3 tools/run_tests.py --filter timer
python3 tools/run_tests.py --filter misc
```

The accuracy runner is fail-closed: an empty selection, timeout, build error, missing state dump, or incomplete result is a failure. Use `--rebuild` when verifying changes that could invalidate generated output.

Blargg `oam_bug` uses its documented external-RAM protocol rather than serial output: `$A001-$A003` must contain `DE B0 61`, `$A000=00` passes, `$A000=80` is incomplete, and any other signed status fails. A missing or malformed signature never passes.

## Accuracy workflow

Use three distinct evidence layers and label them correctly:

1. Repository-owned unit and synthetic tests validate isolated invariants.
2. Differential mode validates generated execution against this project's interpreter.
3. Mooneye, Blargg, SameBoy comparisons, and frame/audio hashes provide independent or higher-level evidence.

Differential mode is not an independent hardware oracle because both paths share runtime devices.

```bash
./output/game/build/game \
  --differential 500000 \
  --differential-log 100000 \
  --differential-fail-on-fallback
```

For stable game-specific repros, record cycle-anchored input and keep the artifacts:

```bash
./output/game/build/game \
  --log-file logs/session.log \
  --record-input logs/session.input

./output/game/build/game \
  --log-file logs/session-replay.log \
  --input "$(cat logs/session.input)"
```

Use `--dump-frames`, `--dump-present-frames`, and `--dump-state` when visual or machine-state evidence matters.

## Interpreter fallback workflow

Measure fallback before optimizing around it:

```bash
./output/game/build/game \
  --log-file logs/interpreter.log \
  --limit 500000 \
  --log-frame-fallbacks \
  --report-interpreter-hotspots \
  --interpreter-hotspot-limit 12

python3 tools/summarize_interpreter_log.py logs/interpreter.log
```

If the summary reports `No interpreter fallback recorded`, the remaining slowdown is in compiled execution or runtime/device work.

Prefer generated `*_metadata.json` sidecars over scraping generated C for names and address mappings.

Data-as-code is the other size lever. `classify_rom_data_regions()` marks ROM byte ranges that look like text or graphics as data before analysis (every window containing a byte must qualify, so code edges are never clipped), and `--pointer-scan strict|off` gates the pointer-derived entry points that otherwise snowball through data. Misaligned decodes of real code are handled after each analysis pass by `resolve_overlapping_decodes()`: per bank it keeps the non-overlapping set of decoded instructions that explains the most ROM bytes (a stream seeded on an operand byte leaves the bytes before its seed unexplained, so the real alignment wins; provenance, direct references and rare opcodes only break near-ties), then re-analyzes with the losers excluded until nothing overlaps. The targets of `--lift-edges`, which are where the ROM's own far calls go, are kept whatever the count says (`vouched_entry_points`), and so are the addresses a recorded run's calls arrived at (the edges file's `entered`); an `--add-entry-point` is weighed like any other seed. A played game is the third source of what is data: `gb_data.py annotations` writes the bytes a recorded run used as they are (drew, played, sent as a bank number, or took for half of an address) as `data` lines for `--annotations`, and never a byte that was only read, since code is read too (`DATA_FILES.md`). A declared range, from an annotation or the cartridge header, stops an instruction that starts in it and one that would run on into it (`runs_into_declared_data`); a classified guess stops neither kind of anchored code. `generated_data_annotations_end_to_end` covers both halves. An address the analysis looked at and decoded nothing at, for either of those reasons or because no instruction has its opcode, is no block (the loop over `block_starts` in `analyzer.cpp` makes none without an instruction): no C is made of it, a call or a jump there goes through the dispatcher, and the interpreter runs it. A block with no instruction has no end address, and what reads one (the fall through the generator emits, the ranges an image is held to) took whatever the block before had left: such a block was a function with nothing in it, which a game that arrived there called for ever. A change to how blocks are made must run `generated_data_undecoded_end_to_end`, which has a game arrive at such an address. Address-sorted run or chain heuristics were tried first and failed: any per-run scoring is dominated by how the run boundaries are drawn, and one wrong two-instruction decision at a resynchronization point cascades. Evaluate any change to these with the interpreter-fallback oracle: run scripted gameplay with `--report-interpreter-hotspots` on the candidate build and compare the fallback sites against a full-coverage build; executed-but-uncompiled code shows up there directly, and `--dump-state` must stay identical apart from `dispatch_fallbacks`.

Generated code size is a first-class concern: measure bytes per guest instruction with an MSVC `/FAcs` listing of one `*_funcs_*.c` chunk before and after an emitter change. The current shape per instruction is one operation, one `ctx->pc` store, one `gb_tick_N(ctx)` call, and one `gbrt_generated_safepoint` check; memory instructions use one `gbrt_timed_bus_*` call. `gb_tick` folds `single_step_mode` into `ctx->stopped`, so generated code must not add separate single-step checks when cycle counting is on. `--compact-resume` keeps resume points at block starts only; validate it by comparing `--dump-state` output against a default-mode build over the same input, and remember that `--differential` single-stepping of a compact build mostly runs the interpreter.

## Recompiler debugging

When analysis hangs, misses code, or emits implausible output:

```bash
./build/bin/gbrecomp roms/game.gb --trace
./build/bin/gbrecomp roms/game.gb --limit 10000
```

Then:

- inspect `[ERROR] Undefined instruction` diagnostics
- use `--add-entry-point bank:address` for a known missed target
- use `--no-scan` to isolate aggressive data-as-code discovery
- use `--symbols` for naming, not as blanket proof that every ROM label is callable
- use `.sym` directives or `--annotations` for trusted function, label, and data boundaries

The Nintendo logo and cartridge-header ranges are built-in ROM data. Keep analyzer state conservative at joins and calls; an unknown target that dispatches safely is preferable to a confidently wrong bank. The one place a bank is taken from less than the joined state is a home-bank CALL or JP whose ways in disagree: it is bound to the bank the bytes right before it select (`bank_selected_just_before`, `ld a, n` then a write to the bank register). That is sound only because a bound target is guarded by the mapped bank at run time (`bank_guard_prefix`), so the guard has to stay.

## Performance workflow

Do not benchmark a normal interactive window with wall-clock timing. Use:

```bash
python3 tools/benchmark_emulators.py roms/game.gb \
  --recompiled-binary output/game/build/game \
  --frames 1800 \
  --repeat 5 \
  --warmup 1 \
  --json-out logs/game-benchmark.json
```

The helper builds a dedicated optimized generated binary by default. `--benchmark` is a reduced-workload core profile: it disables pacing, host presentation, audio emulation, final RGB conversion, and pixel rasterization while retaining CPU/device timing work. Never present it as full interactive-runtime performance, and compare only matching profiles.

When a change is intended to reduce generated/runtime transitions, configure the generated project with `-DGBRECOMP_ENABLE_PERFORMANCE_COUNTERS=ON` and run it with `--report-performance-counters`. Add `--estimate-visibility-regions` only for the separate conservative region-estimator capture; it is intentionally more expensive than basic attribution. These counters are diagnostic-only and do not replace state, frame, PCM, or independent hardware evidence. Keep normal release measurements instrumentation-off.

For a reproducible full-headless attribution/build-footprint artifact, use `tools/run_nl0_profile.py` with a cycle-anchored file under `tools/profiles/`. It creates fresh counters-off and counters-on Release builds, checks repeated state hashes, records ROM/input/executable hashes and feature flags, measures build/runtime wall and process-tree RSS, and samples symbol coverage where supported. Summarize raw logs with `tools/summarize_nl0_profile.py`; use `tools/compare_nl0_controls.py` for the profiling-off regression gate. The symbolized diagnostic profile leaves IPO off by default and must not be compared to the ordinary reduced-workload benchmark profile.

Use `--no-recompiled-autobuild` only when measuring the exact binary already on disk. A result near 60 FPS usually indicates a stale or incorrectly configured run.

For NL-1 timer regression checks, compare the default arithmetic timer against `--scalar-timer` in the same generated executable. `tools/compare_nl0_controls.py` accepts repeatable `--before-arg` and `--after-arg` options and rejects divergent final-state hashes. The retained result and exact gate are in `docs/NL1_ARITHMETIC_TIMER_RESULT_2026-07-14.md`.

For APU scheduling regression checks, compare the default batched path against `--eager-audio` in the same generated executable. A retained result requires identical deterministic PCM and APU state across fine/coarse, HALT-heavy, CGB double-speed, MMIO-observer, and DIV-reset boundaries before applying the three-game performance gate.

For generated-build footprint work, use `tools/profile_generated_build.py` rather than a shell `time` around Ninja. Generated Ninja projects limit executable-target compilation to eight jobs by default; override with `-DGBRECOMP_GENERATED_COMPILE_JOBS=<n>`, or use `0` to disable the pool. Compare source bytes/files, cold wall time, compiler process-tree RSS, executable/loadable size, and runtime separately.

For scene-specific slowdown investigation, combine `--debug-performance`, `--log-slow-frames`, `--log-slow-vsync`, and `--log-lcd-transitions` with recorded input.

## Multi-ROM, Android, and releases

Directory input generates a shared SDL + ImGui launcher. Validate both graphical default behavior and `--list-games` / `--game <id>` scripting when launcher code changes.

Android output is single-ROM, landscape, controller-first, and `arm64-v8a`. It requires an external SDL2 source checkout through `SDL2_SOURCE_DIR`; follow `ANDROID.md` rather than inventing a separate build path.

Release archives (`native-console-<platform>-<arch>`) must contain every console's recompiler and runtime folder listed in `CONSOLES` in `tools/create_distribution.py`, the hub, the root license, and `native-console-release.json` with each file's hash and each recompiler's `--version-json` identity. A release change is incomplete until `tests/test_release_bundle.py` passes on the extracted archive: from a relocated directory it recompiles, builds, and runs one test ROM per console (repository-owned or MIT, never a user ROM).
