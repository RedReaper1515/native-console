# Nintendo 64 (in progress)

> **Not playable yet.** Games build and may start, but expect wrong
> graphics, missing sound and crashes. The hub marks Nintendo 64 games the
> same way.

`n64recomp` turns `.z64`, `.n64` and `.v64` ROMs into C that links with the
N64 runtime. The VR4300, the RSP, the RDP (a C port of parallel-rdp's
rasteriser), the VI's output filters (a C port of parallel-rdp's VI stage),
the interfaces, the PIF and the cartridge saves are in place.
krom's CPU, FPU and RSP test ROMs pass both interpreted and recompiled, on
Linux and on Windows.

The first commercial game, The Legend of Zelda: Ocarina of Time (USA,
Rev 2), boots through its own IPL3 and CIC-6105 check, plays its attract
sequence, creates a file, runs the whole intro and reaches play in Link's
house, with sound; the hub imports it, builds it, captures a cover and
keeps its save across a rebuild. The plan, phase gates, what each hardware
nuance is tested by, and the current results are in
[docs/N64-PLAN.md](N64-PLAN.md).

## Layout

```text
runtimes/runtime-n64/      VR4300 core (interpreter + shared instruction handlers),
                  machine (memory map, MI/VI/AI/PI/RI/SI, scheduler), RSP,
                  RDP, PIF and saves, recompiled-code dispatcher, headless
                  runner, SDL2 frontend and overlay menu (platform/)
recompilers/recompiler-n64/   n64recomp: profiler, analyzer and C emitter
tests/n64/        VR4300 vectors, CPU/RSP/RDP unit tests, test-ROM baseline,
                  recompiled fixture, menu self-test
tools/n64/        test-ROM runner, recompile suite, RDP image comparison,
                  vector and game-database generators
```

## Using it

The hub does all of this for a ROM dropped on it. To try a game you own
end to end from a shell (the interpreter with and without IPL3, then a
profiled native build, its native share and a `--differential` check),
with saves kept in a scratch folder:

```bash
python tools/n64/try_game.py "path/to/Game (USA).zip" --frames 1800
```

The ROM is copied to `output/n64-try/<name>/`; the report and the last
frame of each run (as .bmp) go to `logs/n64-try-<name>.txt` and
`logs/n64-try-<name>/`.

By hand:

```bash
./build/bin/n64recomp game.z64 -o output/game --profile output/game-profile/boot.txt
cmake -G Ninja -S output/game -B output/game/build -DCMAKE_BUILD_TYPE=Release
ninja -C output/game/build
./output/game/build/game                                    # window, sound, input
./output/game/build/game --frames 600 --dump-frame last.ppm --save-dir scratch
./output/game/build/game --differential --frames 600 --save-dir scratch
./output/game/build/game --coverage --frames 3000 --auto-input --save-dir scratch
```

### What gets compiled

N64 code runs from RDRAM, where the game copies and decompresses it, so
`n64recomp` compiles from pictures of RDRAM, not from the ROM:

- **The profile.** `--profile FILE` first runs the ROM in the interpreter
  for 3,000 frames (`--profile-frames N`) under a built-in input script and
  writes a trace: where execution entered, the 4 KiB pages it ran from as
  they were at that moment, and all of RDRAM as the run left it.
- **The whole image.** In that last image the analyzer follows a function
  across pages and follows calls into code the run never reached, so most
  of a game's main code segment is compiled from one short profile. A page
  snapshot is compiled only where the image no longer holds its code (an
  overlay since replaced).
- **Learning from play.** Whatever no trace covered runs in the
  interpreter. While a recompiled game is played in its window, the
  interpreter notes where it was entered and the page it ran from, and on
  exit adds that to `<id>.trace` beside the save (`--no-learn` turns it
  off; compiled code is not slowed). The next build compiles it: the hub
  passes the file to `n64recomp` and keeps it across rebuilds, so play a
  while, then rebuild. By hand, pass it with `--trace FILE`; the headless
  runner writes the same file with `--learn-out FILE`.
- **Checked by its bytes.** Every compiled function carries the bytes it
  was compiled from and runs only while RDRAM holds them at the address it
  was compiled for; a store or DMA into them sends it back to the check.
  Code that loads somewhere else than it did in the trace (an actor
  overlay at another heap address) runs in the interpreter until a trace
  records it there.

`--coverage` reports the native share of the instructions that ran, and
where the interpreter was entered most. Small instruction handlers are
inlined into generated code and the large ones (memory, the FPU, anything
that can raise an exception) are called; `--inline-handlers` inlines all of
them, for somewhat faster code and a build several times slower. Without a
project, `n64_play game.z64` plays any ROM with the interpreter and
`n64_run game.z64` runs it headless.

The ROM is compiled into the executable. No firmware is needed: the
runtime does the PIF boot ROM's part itself and then runs the cartridge's
own boot code (IPL3, part of the ROM), so the boot checks of games such as
Ocarina of Time see what they expect. `--hle-boot` skips IPL3 instead. The
save is `<id>.sav` beside the executable (EEPROM, SRAM or FlashRAM, then
four Controller Paks); the game database picks the save type.

### The picture

The picture is what the console's video interface puts out, not the bare
framebuffer. `runtimes/runtime-n64/src/n64_vi.c` applies the filters the game's
VI_CONTROL selects: anti-aliasing from the coverage the RDP leaves in each
pixel, the dither filter (which takes the RDP's dither pattern back out of
16-bit pictures), the divot filter, bilinear scaling by X_SCALE and
Y_SCALE, gamma and gamma dither. They follow parallel-rdp's VI shaders at
native resolution; gamma dither's noise is its hash of the pixel's position
and the frame number, so frame dumps stay deterministic. Console Video
Filters in the overlay menu's display settings (`--vi-raw` for one run,
headless or windowed) shows the framebuffer's own pixels instead, with
nearest-neighbour scaling: sharper and grainier.

**Internal resolution.** The RDP can draw a second picture at two or four
times the game's resolution: Internal Resolution in the settings menu, or
`--internal-scale 2` or `4` for one run. A 320 x 240 game is then drawn at
640 x 480 or 1280 x 960: edges, texture filtering and shading are worked
out at the finer grain, as parallel-rdp's upscaling does. The console's own
picture is still drawn, by the same code as before, and is all the game can
read, so the game runs exactly as it does without (the same RDRAM, the same
`--dump-state`); the window shows the larger one. Rectangles (most of a
game's 2D: text, menus, the HUD) are drawn at the console's size, as is any
picture the game's own code wrote into the framebuffer. Screenshots and the
hub's covers stay the console's picture. `--dump-large FILE.ppm` writes the
larger picture headless.

The larger picture is drawn after the console's, a whole picture at a time
on a background thread while the game runs on. Ocarina of Time's opening,
interpreted, on a 20-core desktop: 4.4 ms a field at 1x, 5.7 ms at 2x and
10.3 ms at 4x with nothing limiting the speed, and at full speed in the
window no audio buffer ran dry at any of them in 1,800 fields. 4x keeps 16
copies of RDRAM (about 270 MB in all).

### Options

Headless options (the runner; any of them selects it over the window):
`--frames N`, `--until-gpr rN=VALUE`, `--expect-gpr rN=VALUE`,
`--isviewer`, `--expect-isviewer STR`, `--fail-isviewer STR`,
`--dump-frame FILE.ppm` (with `--dump-every N` also `FILE_00000N.ppm`,
...), `--dump-fb FILE.ppm`, `--dump-state FILE`, `--dump-audio FILE.wav`,
`--dump-save FILE.sav`, `--keys FRAME:BUTTONS[:N]`, `--auto-input`,
`--differential`, `--coverage`, `--trace-out FILE`, `--learn-out FILE`,
`--trace-last N`, `--perf` (host time in the CPU, the RSP, the RDP and the
scan-out), `--benchmark`, `--quiet`, `--hle-boot`, `--vi-raw`, `--save-dir DIR`,
`--internal-scale 1|2|4`, `--dump-large FILE.ppm`,
`--headless` (no effect beyond choosing the runner). The runner reads a
save from `--save-dir` and never writes one.

Window options: `--scale N`, `--fullscreen` and `--mute` (each this run only),
`--save-dir DIR`, `--limit-frames N`, `--screenshot-prefix P`,
`--audio-stats`, `--prefs FILE`, `--no-learn`, `--vi-raw`,
`--internal-scale 1|2|4` (this run only),
`--display-shot FILE.bmp` with `--display-size WxH`. `--interpreter` works
in both.

Controls (rebindable in the menu): arrows = analog stick, X = A, C = B,
Z = Z, Enter = Start, A / S = L / R, I J K L = C buttons, T F G H = D-pad,
Tab = fast forward (hold). Escape or F10 opens the menu (the game pauses);
on a controller Guide or L3 do. F9 shows an FPS counter in the window's corner (frames per second and the
game's speed, 100% being full speed; also **Show FPS Counter** in the menu). Preferences are kept in `n64_prefs.ini` in
the per-user app data folder, shared by all N64 games.

## Tests

```bash
python tools/fetch_n64_tests.py                 # pinned suites into roms/n64/ (local only)
ctest --test-dir build -R n64                   # vectors, unit tests, ROM baseline, fixture
python tools/n64/run_n64_tests.py --runner build/bin/n64_run --baseline tests/n64/rom_baseline.txt
python tools/n64/recomp_suite.py                # every test ROM recompiled: verdict, frame, --differential
python tools/n64/compare_rdp_tests.py --runner build/bin/n64_run
```

`n64_vi` checks each VI stage against hand-worked values and whole frames
against a transcription of parallel-rdp's shaders. For the internal
resolution, `n64_rdp` draws its random scenes at 2x and 4x and requires
RDRAM, the hidden bits and the RDP's state to be the console's own, and the
larger picture to be the same through the pixel-by-pixel path, the fast
path and sixteen threads; it also checks the larger picture by its rules
(an edge at the finer grain, shading at quarters of a pixel, pixels the
game wrote). `n64_vi` checks that the console's frame does not change with
the scale and that the larger frame does not depend on the thread count. `n64_rsp_fast` runs the
RSP's SSE2 vector unit, its decoded-instruction run loop and its memory
shortcuts against the plain handlers and a plain interpreter (6.4 million
checks, self-modifying IMEM included); `n64_rsp_reference` and
`n64_rsp_fast_reference` run both RSP tests on the portable path that
hosts without SSE2 use.

`fetch_n64_tests.py --dest DIR` with `-DN64_TEST_DATA_DIR=DIR` at configure
time shares one download between checkouts; without the data the test-ROM
tests are not registered.

The fixture ROM (`tests/fixtures/make_n64_rom.py`) is assembled by the
repository's own MIPS assembler, so `n64_recompile_fixture` needs no fetched
data: fourteen cases including overlays loaded by DMA, a store into code
that already ran, a return through ERET, an idle loop ended by the timer
interrupt and a jump into a branch the recompiler leaves to the
interpreter. It is built three ways (from the boot image, from a profile,
and from the trace a build records while it runs) and each must pass
interpreted, recompiled and in `--differential`.

## What is not done

- One game has been run, as far as its first room. Compatibility beyond
  Ocarina of Time is unknown, and so is speed in its busier scenes: the
  scripted route runs at about 270 frames a second without a frame limit
  on a 20-core desktop.
- Linux, SteamOS and macOS builds (P7) come after Windows.
- Relocatable code that loads at an address no trace recorded runs in the
  interpreter; nothing matches such code by its relocations yet.
- Timing: caches, pipeline stalls, the RSP's dual issue and the RDP's speed
  are not modelled (krom's TIMING tests fail); interrupts are taken at the
  next memory or COP0 instruction rather than between any two.
- The VI reads its registers once a field (no per-scanline H_START or
  X_SCALE), and its filters have not been compared with a console or with
  parallel-rdp on a graphics card.
- Save states, the Rumble Pak and Transfer Pak, the 64DD, and the RTC.
- The RDP is a software rasteriser on the CPU, sharing large primitives
  between threads. `N64_RDP_THREADS=N` in the environment
  sets the thread count (1 is serial; the default is half the host's
  processors, at most 8), `N64_RDP_SPIN_US=0` stops its helpers spinning
  briefly between primitives, and `N64_RDP_REFERENCE=1` selects the
  pixel-by-pixel path the fast ones are tested against. The picture does
  not depend on any of them.
- Internal resolution is 2x or 4x only (the RDP's arithmetic scales by
  powers of two), has been tried on one game, and leaves rectangles and
  pictures the game's own code draws at the console's size. Its scan-out
  without Console Video Filters waits for the whole larger picture each
  field, so that combination is slower.
- For modders: no symbol maps, function overrides or hooks yet.
