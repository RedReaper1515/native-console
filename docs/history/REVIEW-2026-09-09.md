# Code review: gb-recompiled v0.1.0 (main @ 3b66440)

Reviewed 2026-09-09 against Pan Docs / gbdev hardware behaviour and the
gb-asm-tutorial reference material. Line numbers refer to this commit.
The review was triggered by a real failure: Link's Awakening (DMG, MBC1)
recompiled with v0.1.0 has a solid exit door in Marin's house.

## Headline

The recompiler is well engineered where it is exercised (dot-serial PPU,
timer/DMA/HALT-bug modelling, interrupt entry, mapper register modelling)
and weak where it is not: **the shipped execution mode, free-running
generated code, has no automated correctness net.** `--differential`
single-steps generated code through the dispatcher, which re-resolves the
ROM bank and re-checks interrupts after every instruction. Two real
problems live only in the free-running path and are invisible to it:

1. Home-bank calls into `$4000-$7FFF` are statically bound to bank 1.
2. Native stack depth is unbounded on cross-body `jp` chains.

## 1. Bank inference (recompiler/src/analyzer.cpp) — confirmed bug

**Symptom.** Home-bank code at `00:3E6F` does
`ld hl,$2100 / ld [hl],$02 / call $5FD1`. The emitter produced
`func_01_5fd1(ctx)`. Bank 1's bytes at `$5FD1` are `dec a / ld [$C3C4],a /
ld a,[$DB96] / rst 0`, a jump table, whose entry was read from bank 2's
data, landing in the room-object loader with garbage registers. Four
bytes of the room map (`22 22 C1 C2`, the doorway) became `28 28 28 28`
(solid wall). PyBoy and the built-in interpreter both produce the right
map; only free-running generated code does not.

**Cause.** It is a seed assumption, not a fallback:

- Every home-bank entry point is analysed from
  `mapper_state_for_bank(rom, bank > 0 ? bank : 1)` (analyzer.cpp:1134-1139,
  1146-1151, 1244-1247, 1224, 1005-1008; also `1298-1300` rebinding
  `0:4xxx` work items to bank 1). `mapper_state_for_bank` (415-440)
  hard-codes `mbc1_low = 1`. So the state is *never* unknown for home-bank
  code and `mapper_upper_bank` (471-510) always yields a concrete bank.
- The mapper-write matcher (1543-1575) recognises `LD (nn),A`, `LD (BC),A`,
  `LD (DE),A`, `LDI/LDD (HL),A`, `LD (HL),r`. There is no case for opcode
  `0x36` `LD (HL),n`, even though the decoder emits it as `LD_HL_N` with
  `imm8` and `ld hl,$2100` is already tracked (1414). Link's Awakening's
  bank-switch idiom is exactly this store.
- Unknown-pointer stores are silently ignored (1570 requires
  `mapper_addr >= 0`), which is unsound: state should degrade to unknown.
- `resolved_target_bank` is assigned (1707, 1755) *before*
  `is_likely_direct_branch_target` is consulted, so a rejected target still
  gets a concrete bank.
- The emitter (codegen/c_emitter.cpp:1867-1877 CALL, 1652-1662 JP,
  1767-1778 JP cc) only routes through the dispatcher when the bank is
  `UNKNOWN_BANK`; the static path (1878-1935) never checks
  `gb_resolve_rom_bank` at runtime.

**What I would do.**

- Add the `0x36` case to the matcher (value = `instr.imm8`).
- Seed home-bank entries with an *unknown selected bank* (keep mode/high
  bits known so `$0000-$3FFF` resolution and RST still work). Home-bank code
  then dispatches dynamically until a real mapper write is seen.
- Only assign `resolved_target_bank` when the target validated.
- In the emitter, guard every static call into the switchable window with
  `if (gb_resolve_rom_bank(ctx, target) == N) func(ctx); return;` — a
  one-compare belt-and-braces check that would have made the bug
  impossible regardless of analysis quality.
- Add a debug-build assertion at body entry that the body's bank matches
  the mapped bank; it would have caught this on frame 1.
- Tests: `tests/test_analyzer_mapper_state.cpp` covers `EA nn` and
  `LD (HL),A` only, and only inspects `bank_tracker.switches()`, never a
  CALL's `resolved_target_bank`. Add a fixture `21 00 21 / 36 02 / CD D1 5F`
  asserting bank 2, and a fixture with no mapper write asserting
  `UNKNOWN_BANK`.
- Longer term: callee mapper-state summaries. Today a callee that switches
  banks and does not restore is not modelled (1735, 1746);
  `may_switch_rom_bank` exists per function but is not consulted here.

## 2. Free-running vs single-step (codegen/c_emitter.cpp, runtime)

Every `if (ctx->single_step_mode) return;` (1678-1681, 1691, 1794, 1807,
1893, 1948, 1998, 2043, 2128, 2187, 2443-2445, 2460-2464) plus
`gb_dispatch` breaking after one dispatch means the differential harness
executes a *different program* from the one users run:

- **HALT bug.** Handled in both modes, but by different code: `gb_run_cycles`
  enters through `gb_step` (gbrt.c:5452), which routes the instruction after
  a bugged HALT through the interpreter, while `gb_dispatch`'s own loop
  (3467) never checks `halt_bug`. Blargg's `halt_bug.gb` passes
  free-running. (An earlier draft of this review claimed the opposite.)
- **EI delay.** Free-run is correct; `gb_debug_step` calls
  `gb_handle_interrupts` first (5468-5499), so single-step fires one
  instruction early. The differential therefore diverges from hardware on
  every EI, in the *reference* context.
- **Bypassed fast paths.** `gbrt_fast_forward_visible_ly_wait` is emitted
  under `!single_step_mode` (3706-3715) and rewrites A and all flags; the
  generated `_fast_read8/_fast_write8` (2576-2637) skip the DMA
  `pending && startup_delay <= 4` window that `gb_read8` honours;
  `gbrt_cycles_until_next_event` returns 0 in single-step (gbrt.c:2200).
  None of this is ever compared against the interpreter.

**What I would do.** Give each context an execution mode consulted in
`gb_step`, run *both* contexts free-running for a frame or a scanline
budget, compare with the existing `gb_diff_compare_contexts` at the
boundary, and on mismatch restore the last matching savestate and replay
that window in lockstep to localise the instruction.

## 3. Host stack depth

Callees are invoked as `func(ctx); return;` and continuation after a GB
`ret` is only reached by unwinding to `gb_dispatch`. Depth = GB call
nesting + every cross-body `jp` since the last safepoint. A hot loop
whose `jp` target is a separate body adds a frame per iteration until
`stopped` unwinds. MinSizeRel `-Os` gives sibling-call optimisation on
GCC/Clang; Debug `-O0` and MSVC do not guarantee it. No depth counter,
no `musttail`, no `/STACK` flag. (My own debug instrumentation of the
generated code overflowed the stack instantly on MSVC.) Recommend a
trampolined/threaded dispatch for cross-body transfers, or
`[[clang::musttail]]` where available, plus an explicit stack size in the
generated CMake and a debug depth counter next to
`gbrt_note_generated_direct_transition`.

## 4. Analysis noise and defaults

- `--no-scan` should be the default. `find_pointer_entry_points`
  (984-1044) slides a 2-byte window over every byte of every bank and
  probes every switchable bank for home-bank windows; aggressive scan
  (1945-2040) accepts anything that decodes to a `ret` within a few
  instructions. Result: a function per byte (`func_3282`, `func_3283`, …),
  mid-instruction bodies (`loc_3121: DEC (HL)` is an operand byte), and
  inflated dispatch tables. Track a covered-bytes set and reject candidates
  that start inside a decoded instruction.
- `[ERROR] Undefined instruction` (1613) and `[ANALYSIS] Unresolved JP HL`
  (1920) are unconditional `std::cout`. The diagnostic is already recorded
  as `potential_false_code` with a suggested `data` annotation and exported
  to `*_metadata.json`. Print a summary count; move the lines under
  `--verbose`; drop the `ERROR` label for scan-originated hits.
- `ir_optimizer.cpp` is entirely stubs; `generator.cpp` is dead
  (no header, no callers). Delete or wire up.
- `main.cpp` (2363 lines) carries Android/Gradle templates, a 440-line
  ImGui launcher as a string literal, duplicated OAM-DMA overlay detection
  (also in generator.cpp), a hand-copied ABI table in `print_version_json`
  that can drift from the runtime headers, and unguarded `std::stoul`.

## 5. Runtime bus / CPU (runtime/src/gbrt.c, interpreter.c)

Ranked:

- **High.** DMG OAM DMA blocks `$FF00-$FF7F` and `$FFFF`
  (`gb_oam_dma_blocks_cpu_addr`, 2039-2041). Hardware keeps I/O and IE on
  the CPU-internal bus. `gbrt_execute_halt` reads IE/IF through this path
  and gets `$FF`, so `halt` during an active DMA with IME=0 triggers the
  HALT bug instead of halting; an ISR entered mid-DMA reads LY/STAT/JOYP as
  `$FF` and its IF/IE writes vanish. `tests/test_oam_dma_bus.c` only
  asserts HRAM readability.
- **Medium.** Joypad press clears `halted` unconditionally
  (platform_sdl.cpp:1368-1372, differential.c:266-270); hardware exits
  HALT only on `IE & IF`.
- **Medium.** External RAM is bounds-checked instead of mirrored
  (2651-2655, 2934-2937, 1866-1867): MBC1 8 KiB carts in mode 1 with
  `rom_bank_upper != 0` lose their save RAM.
- **Medium.** STOP keeps PPU/timer clocked and resumes on any `IE & IF`;
  DIV is not reset on STOP or on the CGB speed switch.
- **Medium.** EI promotion happens at the end of the same `gb_tick`; if that
  tick also sets `stopped`, the next scheduler entry services the interrupt
  before the instruction after EI.
- **Low.** The highmem stub mini-interpreter sets `ime = 1` immediately for
  EI (3894-3904); `$FEA0-$FEFF` reads `$FF` (DMG returns `$00`); MBC3 RTC
  writes are wrapped with `% 60 / % 24`; MBC5 RAM enable compares the low
  nibble only; VRAM write blocking keys off `io[0x41]` while reads key off
  `ppu->mode`.

Verified correct: MBC1 remap and mode-1 windows, MBC1M, MBC2 address
decode and 4-bit RAM, MBC3 latch, MBC5 9-bit bank, TIMA overflow delay and
reload, DIV write edge, TAC glitch, P1 select bits, IF upper bits, HALT
bug detection, 20-cycle interrupt entry with cancellation, echo RAM, DAA,
`ADD SP,e` / `LD HL,SP+e` flags, `PUSH AF` low nibble, `RLCA/RRCA` Z=0.

**Structure.** `gbrt.c` is 5,587 lines mixing persistence, tracing,
profiling, mapper, timer, DMA, bus, ALU, scheduler and three ad-hoc
mini-interpreters for RAM-resident code (~570 lines duplicating
interpreter.c and already diverged). Memory decoding is re-implemented in
at least eight places. Mapper type ranges are magic numbers in 10+ sites.
Split by device, introduce `gb_mapper_kind(ctx)`, and route every bus
access through one decode.

## 6. PPU / APU (runtime/src/ppu.c, audio.c, platform_sdl.cpp)

The dot-serial PPU with the "prove-then-batch" span path is the strongest
part of the runtime. Findings:

- **High (APU).** DAC gate uses `nrX2 & 0xF0` (audio.c:849, 857, 879);
  hardware is `& 0xF8`. Any envelope-up-from-zero instrument is silent.
- **High (APU).** NR52 power-off `memset`s `Channel3` including
  `wave_ram` (624-627). Hardware preserves wave RAM; drivers that reset
  the APU on song change lose channel 3.
- **Medium.** LCD off never shows white (`gb_platform_render_lcd_off_frame`
  prefers the last frame, platform_sdl.cpp:3589); with frame smoothing off
  an LCD-off idle loop never yields to the host (`slice_budget =
  0xFFFFFFFF`, c_emitter.cpp:4747).
- **Medium.** DMG STAT-write spurious IRQ not emulated (ppu.c:1907-1913).
- **Medium.** WY latched at mode-3 start instead of mode-2 start
  (ppu.c:1112-1114).
- **Medium.** HBlank DMA never starts in the HBlank it was programmed in
  (gbrt.c:1983-1994).
- **Low.** Sprite data re-read per dot rather than latched; SCX applied
  per pixel; line 153→0 skips the hidden 4-dot mode-0; several APU
  quirks (length-clock on trigger, duty phase on retrigger, wave-channel
  first sample, DMG wave-RAM access, NR43 shift ≥ 14).
- **Dead code.** `ppu_render_scanline` and its helpers (~450 lines) have
  no caller and have drifted from the dot path. Delete.
- **Perf.** `ppu_cycles_until_next_event` returns 1 during mode 3, so the
  CPU event batching collapses for ~40% of every frame. `convert_to_rgb`
  does per-pixel mul/div; use a LUT. Palette remap runs per present.
- **Audio.** SPSC ring is correct. No dynamic rate control, so long
  sessions drift into drops or underruns. Synthesis is point-sampled with
  no band-limiting.

## 7. Tests, CI, docs

- No test runs generated code free-running against an independent oracle.
  Blargg/Mooneye via `tools/run_tests.py` need a gitignored `roms/` tree
  and are not in CI; `.github/workflows/release.yml` runs no `ctest`.
  `docs/ACCURACY.md` is a hand-regenerated snapshot.
- Untested: decoder, IR builder, emitter lowering (bar two cases),
  interpreter flag semantics, `rom.cpp`, `symbol_table.cpp`, CLI parsing,
  `differential.c`, MBC2 entirely, MBC3 RTC, ERAM mirroring, joypad, STOP,
  EI-across-frame.
- 26 of 78 test files are Pokémon Crystal specific; the generic runtime
  ABI hard-codes `GB_PORT_INPUT_TOGGLE_ENCOUNTERS` bound to F3.
- `AGENTS.md` requires `tech_docs/pan_docs.md` and `SameBoy/`, both
  gitignored. README's "versioned runtime snapshot" carries no version or
  hash. `docs/RUNTIME.md` documents `--help` for the generated runtime, which
  has none.
- Runtime CLI parsing lives in the *emitted* `main.c`
  (57 `strcmp` sites in c_emitter.cpp) rather than in `runtime/`.

## 8. Windows / MSVC portability

`runtime/src/gbrt.c` declares `gb_dispatch` with `__attribute__((weak))`
so a bare runtime can link without generated code. MSVC has no weak
symbols, so every runtime unit test (`test_hdma_timing`,
`test_mbc5_runtime_bank`, … 40+ targets) fails to link on Windows with
`LNK2019: unresolved external symbol gb_dispatch`, and `ctest` reports them
as "Not Run". The recompiler-side tests build and pass. A `gbrt_dispatch_stub.c`
linked only into the runtime tests, or a function-pointer hook set by the
generated `main`, would make the suite portable.

*Resolved 2026-09-10:* `gbrt.c` now provides the fallback through
`/ALTERNATENAME` on MSVC, the SDL-dependent tests copy `SDL2.dll` beside
themselves, and the tests that assumed `unistd.h` or SDL's `main` redirect
were made portable. The Python-driven tests followed: scripted stand-in
executables get a `.cmd` wrapper on Windows, generated projects copy
`SDL2.dll` beside their executables, CTest forwards `SDL2_DIR` to them,
and the harnesses accept MSVC's `cl`. The whole suite passes on Windows.

## Verification of the fix in this fork

Branch `fix/home-bank-call-resolution` implements items 1 of the order of
work below: `LD (HL),n` mapper-write recognition, unknown-bank seeding for
home-bank entries (only `$0100` starts in the reset state), no static
binding of rejected targets, a runtime bank guard on every statically
bound transfer into switchable ROM, and `tests/test_analyzer_home_bank_calls.cpp`.
Regenerating Link's Awakening (USA/Europe Rev 2) with it and no
post-processing: home-bank calls into the window drop from 58 unguarded
static bindings to 3, all guarded; the room map holds `22 22 C1 C2`; Link
takes the shield from Tarin and exits to overworld room B2 with no
interpreter fallbacks recorded.
